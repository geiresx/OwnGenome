# Changelog

Each release's notes. From 1.0.0 on, a major or minor release has hand-written notes under `docs/releases/`, and the release workflow uses them as the release body. Older releases list their commits on GitHub.

## Unreleased

- Steps 06, 17 and 31 (and the CLINVAR_CDNA_CHECK and COMPHET_PHASE modules) now read the reads at a variant with the Rust `og` binary: `og cdna check` (the cDNA read check of each ClinVar or CPSR hit), `og cdna scan` (the genome-wide cDNA scan) and `og comphet phase` (the phase of each compound-het pair). They replace `bin/cdna_scan.py` and `bin/comphet_phase.py`, which are gone, and the read check of `bin/clip_check.py`, which keeps only the names the report imports. Step 32 and the PYPGX module read the BAM's contig names with `og bam contigs` instead of a pysam one-liner. These steps no longer need pysam; they still run in `PYPGX_IMAGE`, so CI can run the deleted Python beside `og`. The tables, file names and options stay the same; 45 parity cases on made-up BAMs hold them. What changes:
  - The cDNA scan lists its loci in the BAM's contig order, then by position. It sorted the contig names as text, so `chr10` came before `chr2`. Only the row order changes.
  - The scan reads each record once, even when it spans two exon regions, and reads the contigs on several threads. On a synthetic BAM of 2 million reads and 59,940 exons it takes 1.3 s and 22 MB where the Python took 2.2 s and 82 MB.
  - Each table is written to a temporary file and renamed, so a failed run leaves no half-written table.
  - A row of step 31's per-variant table with fewer columns than its header stops `og comphet phase` with exit 2 and the line. The Python crashed with a traceback.

- The copy-number engine now runs in the Rust `og` binary, as `og cn bed`, `og cn call`, `og cn intervals`, `og cn check-bam`, `og cn marker-regions` and `og cn marker-read`. That covers step 35's depth counts (HBA, the gene-dosage rows, CYP21A2, the interval rows) and its SMN1 marker, step 46's KIV-2 count and 4925G>A reading, the RHD regions of step 41 and the ALT-contig check of steps 32 and 35. They replace `bin/hba_copy_number.py` and `bin/lpa_kiv2.py`, which are gone, the commands of `bin/copy_number.py` and the marker reader of `bin/traits_report.py`. Two parts stay in Python for now: step 41's report makes the RhD call with the catalog reader and `assess()` of `bin/copy_number.py`, and step 32's CYP2D6 depth check is its own tool. `bin/traits_report.py` keeps `MARKERS` for the summary. Every table, file name and option a step uses stays the same; the parity cases in `tests/parity` hold every output that changed on purpose:
  - Step 46: the KIV-2 4925G>A reading is made in the same call as the count and judges the aligner on the count's own MAPQ 0 share. Before, it read the share the count table prints, rounded to three places, so at a share just under 0.20 the count said not assessed while the marker still read `present`. Both now say not assessed.
  - Step 35: the SMN1 marker message takes the SMN1 psCN from the first row of the SMN table that covers exon 7, the rule of the Paraphase comparison. It took the last such row, so a table with two rows over exon 7 made the two read different counts.
  - Steps 35 and 46: a status the HBA or LPA table layout did not name (a catalog edit could give one) now writes `not assessed: <reason>`. The HBA table wrote `called` with no count, and the LPA table stopped with an error.
  - A catalog row with a `more=` reading and no numbered reading is refused when the catalog loads, naming the row. Before, a call that reached it failed without naming the row.
  - `og cn call --sex` reads a gene row on chrX or chrY against the sample's count there. The Python call had no sex, so such a row could only read `sex_unknown`. No row of the shipped catalog is a gene row on chrX or chrY.
  - The tables are written to a temporary file and renamed, so a failed run leaves no half-written table.
  - `og cn bed` and `og cn marker-regions` exit 2 when they cannot write the region list, so a step never reads a truncated list.
  - `copy_number.py call --json` is gone with no replacement: no step passed it.
  - Error messages about a wrong regions table say to make it with `og cn bed`.

- The opt-in steps 45, 47, 48 and 50 to 53 now read their tool's output with the Rust `og` binary: `og y str-bed` and `og y str-report` (step 45), `og viral report` (47), `og exomiser prepare` and `og exomiser report` (48), `og mei report` and `og mei annotsv-input` (50), `og mocha report` (51), `og vntyper report` (52) and `og locityper report` (53). They replace `bin/ystr_report.py`, `bin/viral_report.py`, `bin/exomiser_report.py`, `bin/mei_report.py`, `bin/mocha_report.py`, `bin/vntyper_report.py` and `bin/locityper_report.py`, which are gone. og is static, so each step still runs in the image it ran in. The tables are the same, byte for byte, on the 123 parity cases, except where a line below says otherwise. Every output is written whole or not at all, and an input a step cannot read stops it with one `ERROR:` line, not a Python traceback.
  - Step 48: the summary printed at the end of `og exomiser report` has one line per rank. The Python cut it by variant count, so a rank with several variants could push the closing note in or out. The text file is unchanged.
  - Step 50: the depth of each catalog window is its own. The Python looked it up by gene and chromosome, so two windows of one gene on one chromosome both got the last one's depth. The shipped catalog has no such pair, so its results do not change.
  - Step 51: `calls_mocha` in the summary counts this sample's calls only. The Python counted every row of MoChA's call table, so a table of several samples gave a wrong count. A call row shorter than the header now stops the step with exit 2 and the file and line.
  - Step 52: a coverage table with a negative mean depth stops the step with exit 2 and says so. The Python crashed.
  - Step 53: a `res.json.gz` that holds JSON but not an object, or a genotype that is not text, now reads "not called" with the reason. The Python crashed and wrote no table. A loci BED start written in non-ASCII digits is refused with its line.
  - Step 45: a panel region with a motif length under 1, or a negative copy number, is refused with the marker's name. The Python crashed on the first and used the second.
  - Steps 47, 50 and 51: an unreadable input stops with `ERROR: <message>` on stderr, where the Python wrote `<script>.py: <message>` or a traceback. The exit codes are the same.

- Step 38 (family analysis) and the Nextflow family workflow now run in the Rust `og` binary: `og family plan`, `prepare`, `check`, `report` and `segments` replace `bin/family_report.py` and `bin/family_segments.py`. `family_segments.py` is gone. `family_report.py` keeps only the pedigree, kinship and PAR rules that step 39, the IBD report, the pedigree drawing and the SV steps still import, and `og dev remnants` fails if anything else comes back. `og family report` reads the joint VCF once (twice at the same time with `--phased`) and compresses each child's inheritance table on its own thread. On a synthetic five-person family of 1,000,000 sites it takes 0.9 s and 26 MB instead of 24 s and 85 MB, and at 5,000,000 sites 4.3 s and 93 MB instead of 161 s and 307 MB. Every table, map and report is the same as before, by content. What changes:
  - A joint VCF that is not sorted (a position that goes back, or a chromosome that comes back) now stops `og family report` and `og family segments` with exit 2 and names the two records. The Python split the chromosome map at the wrong places and said nothing.
  - The inheritance tables are gzip level 6, not 9. They decompress to the same bytes.
  - Smoothing the chromosome map takes O(R log R) time instead of O(R²) in the number of runs, with the same merges in the same order.
  - A missing input file, a genotype or position that is not a number, or a record before the `#CHROM` line now stops with an `ERROR:` line and exit 2, not a Python traceback.
  - Each output is written whole or not at all: a run that stops leaves no part-written table behind. A read-only `family_plan.tsv` is replaced; a folder that cannot be written still stops the plan.
  - Step 38, step 39 with a families file, `run-all.sh` with `FAMILIES` and the family workflow now need `og` (`scripts/setup.sh --og`).

- The family page now keeps a child's results to act on closed, as the child's own page does, and what it shows of a child no longer depends on which result is closed or where it lies. While a child has a result still closed, or the page cannot read the child's results, these close for that child, one box each: the painting's grandparents (every stretch drawn from its parent alone), the chromosome map image, all de novo and compound-het rows, the child's medicines and HLA cells in the side by side, and the carrier screen of a couple the child is part of. Each "Show the result" opens one result; the places come back once the last one is opened, and a reload closes them again. While the results cannot be read, each box opens only its own place. On a child's page, a copy-number dot and a card's fact that name a closed result's gene now close with it too, on a phone in the card's line as well. `results.json` adds `veil.spans`, `veil.facts` and `veil.widget`; nothing is renamed or removed. The veil is still a browser veil: `results.json` and `family.json` hold every row.
- Step 40, the 23andMe and AncestryDNA raw-data files, now runs on the Rust `og` binary: `og consumer export`, `og consumer build-sites` and `og consumer check` replace `bin/export_consumer.py`. On a synthetic gVCF of 552 MB (32 million records) with 617,044 sites it takes about 2 s and 43 MB in a Linux container on 4 cores, where the Python took 30 s and 660 MB; the files hold the same rows. `setup.sh --consumer-sites` reads dbSNP on 4 cores without the grep pass. The zips are now the same bytes for the same day (`--date`, else `SOURCE_DATE_EPOCH`, else today). Fixes: a call of three or more alleles stops the export with the site, instead of a file the strict reader refuses; two dbSNP records of one rsID at one position have their ALT alleles joined before the strand test; a bad site row or an unreadable zip is reported with the file and line instead of a traceback; a good export removes the `.txt` files a failed one left. The musl builds of `og` use the mimalloc allocator, which keeps a long multi-threaded read at its live memory. Step 40 needs `og`: `scripts/setup.sh <genome_dir>` builds it, and `scripts/setup.sh --og` builds only it.

- Steps 21, 32 and 9b (and the CYRIUS, PYPGX and STRANGER_RFC1 modules) now run the CYP2D6 depth check and the RFC1 motif count with `og`, and `bin/cyp2d6_depth_check.py` and `bin/rfc1_motif.py` are gone. A run that reaches these steps needs the binary: run `./scripts/setup.sh --og` once after setup and after each pull; without it the step stops with `og is not built`. The output files, their names and formats do not change; in CI, every e2e case that runs these steps in bash checks `og` against the deleted Python, byte for byte.
- Step 33's estimate of mosaic loss of chrY or of one chrX now runs in the Rust `og` binary: `og qc sex-loss` replaces `bin/mosaic_sex_loss.py`, which is gone. The `mosaic_*` rows it adds to `qc/<sample>_sample_qc.tsv` are the same, byte for byte, down to the last digit of CPython's exact variance, and it reads a whole genome's mosdepth windows about three times faster. Step 33 and the Nextflow `SAMPLE_QC` process now need `og`: run `scripts/setup.sh --og` once. Three things change on purpose:
  - A depth of `nan` or `inf` in the mosdepth windows is now named in `mosaic_reason` as unreadable. Before, the median of a block with `nan` depended on where it sat.
  - A VCF site whose `AD` adds up past 4,294,967,295 reads is now skipped. Before, it stopped the tool with an `OverflowError`, and the table got no `mosaic_*` rows.
  - A regions file or VCF that is not UTF-8 is named in `mosaic_reason` with its line number, not Python's byte offset into its read buffer. A step 33 table that is not UTF-8 still stops the tool (exit 1), now with its line number instead of Python's `UnicodeDecodeError` text.
- The checks CI runs on the pipeline itself now run in the Rust `og` binary: `og dev contract` (the output contract, from `scripts/ci/check-output-contract.py`), `og dev schema` (a `summary.json` against its schema, from `tests/schema/validate.py`) and `og dev report-only` (the report-only error strategy, from `scripts/ci/check-report-only.py`). The two Python checks and their two test files are gone; their checks are cargo tests in Guard's `rust` job. `tests/schema/validate.py` stays only as an in-process helper of three Python test files (the unit-tests job has no `og`), with the same rules as `og dev schema`. Each now fails on what it let pass:
  - `og dev contract --static`: a `nextflow_schema.json` default of another JSON type than `nextflow.config`'s value (`0` for `false`, `1` for `true`) now fails. A results file the run check cannot read (a truncated gzip) is a `FAIL` line that names it, not a traceback. Commented-out Groovy no longer counts.
  - `og dev schema`: `additionalProperties: false` now refuses a key the schema does not list; `true` no longer matches `enum: [1]`; NaN fails `minimum`. A schema with an unknown keyword or type name, or a `$ref` to nothing or back to itself, anywhere in it, is now exit 2 (a broken schema), not a pass or a traceback. A document that is not JSON prints `ERROR:` and exits 1.
  - `og dev report-only`: a `//` inside a string is no longer read as a comment, and a nested brace in the strategy closure, or a setting before it, no longer hides a `withName` block.
  - `--repo` defaults to the current folder for `og dev contract` and `og dev report-only`.
- Step 06's ClinVar screen runs in the Rust `og` binary, with one table of ClinVar review stars: `og clinvar join-adjacent` (the combined-allele joiner; its `build` mode reads the reference itself, in place of the `bcftools +fill-from-fasta` pipe), `og clinvar hits` (the console TSV) and `og clinvar deep-intronic` (the always-report list) replace `bin/clinvar_join_adjacent.awk` and `bin/clinvar_hits.awk`, which are gone. On 19 cases og writes what the awk wrote, byte for byte, with one fix: an empty GENEINFO segment (between two `|`) is left out of the TSV's gene column, as the run summary already did. Step 06 now needs `bin/og` (`./scripts/setup.sh --og`) and an uncompressed reference with its `.fai`, the documented default; a gzip reference is refused.
- Step 25's scoring files are written by the Rust `og` binary: `og prs format` replaces `collect_summary.py prs-format` in `PRS_PREPARE` and `scripts/25-prs.sh`. It reads one score at a time, so `PRS_PREPARE` peaks at 0.7 GB instead of 11.5 GB on the default scores and asks for 2 GB instead of 16 GB, and it runs in seconds instead of minutes. The files it writes hold the same rows, labels and notes. Fixes: two scoring files with one PGS id (`PGS1.txt` and `PGS1.txt.gz`) now stop the step with `ERROR: PGS1 has two scoring files in DIR: PGS1.txt, PGS1.txt.gz`, where the second overwrote the first and both were counted; a score list that is not UTF-8 gives `ERROR: <file>: not UTF-8 at byte N`, not a Python traceback; a scoring file whose name and `#pgs_id` differ takes its label from the list's row for the `#pgs_id`, as its sex and evaluations already did. With `--keep-ambiguous`, a malformed `.fai` line (`ERROR: cannot read the reference REF and its .fai: .fai line N: ...`) or a `.fai` that does not match the FASTA (`the .fai does not match the FASTA: ...`) now stops the step, where the Python skipped short `.fai` lines and read whatever byte sat at the offset. The score files are gzip level 1 instead of 9: the same text, a little larger.
- Step 49 (clonal haematopoiesis) now prepares the CHIP gene models and writes its two tables with the Rust `og` binary: `og chip prepare`, `og chip report` and `og chip check-table` replace the commands of `bin/chip_report.py`, which keeps only the detection limit and the column names the reports import. On Ensembl 116's full GFF3, prepare takes 1.7 s and 6 MB instead of 15 s and 20 MB. The two tables, `chip.gff3` and `chip.bed` are the same, byte for byte. What changes: a missing input file or a position that is not a whole number stops with an `ERROR:` line and exit 1, not a Python traceback, and each output is written whole or not at all. Step 49 now needs `og` (`scripts/setup.sh --og`).

- VEP consequence ranking (steps 23 and 31) and the gnomAD constraint join now run in the Rust `og` binary, inside `BCFTOOLS_IMAGE`: `og vcf csq-rank` replaces `bin/csq_rank.awk` and `og table constraint-join` replaces `bin/constraint_join.awk`, which are gone. Neither awk program runs on the host anymore (step 23 still uses the host's `awk` for small table edits), and the ranker is no longer the slow stage of step 23's main pipe. Steps 23 and 31 now need `og`: `scripts/setup.sh --og` builds it. Their output is the same, byte for byte, except for these changes.
  - The seven `##INFO=<ID=PGP_...>` header descriptions end in `(og vcf csq-rank)`, not `(bin/csq_rank.awk)`. No tag, value or column changes.
  - A ranking floor that is not a number, or a `--keep` other than `all` or `noncommon`, is a usage error (exit 2). awk read such a floor as 0.
  - An empty constraint file now stops with `ERROR: the constraint table <file> is empty` (exit 3). awk read the summary table as the constraint file and blamed the wrong file.
  - An unreadable input is reported with its path and the reason: exit 2 from `og table constraint-join`, exit 1 from `og vcf csq-rank`.
- The STRchive catalog, Exomiser's zips and the genetic map are now set up by the Rust `og` binary: `og str catalog` (replaces `bin/strchive_convert.py`, which is gone), `og setup unzip` and `og setup genetic-map` (replace two Python programs inside `scripts/setup.sh`). The catalog and its ranges table are the same, byte for byte, and so are the unpacked Exomiser data and the maps. `setup.sh` builds `og` first when these need it. The STRchive catalog is converted once more after this update, because its stamp now names the converter's format instead of the Python file's hash.
  - Steps 26b and 51: each genetic map file is written whole or not at all. Before, a setup killed while it wrote a map could leave a truncated `.rfmix.map` that every later setup took as done. Step 26b's maps now carry a stamp, `maps/DONE`, written last; an install without it, or with a map file missing, writes every map again. `tests/test_setup_fine_maps.sh` checks this on a cut-short map.
  - `setup.sh --exomiser-data`: a zip member whose name leaves the folder (an absolute path or `..`) is refused, and nothing is unpacked. Python's `extractall` wrote it elsewhere, under a name with those parts dropped.
  - A genetic map row with fewer than four fields, a STRchive record with a missing coordinate, a locus structure with no repeat, and an extra STR locus whose `LocusId` or `VariantId` is not text now stop with exit 2 and a message, not a Python traceback.
  - A damaged zip whose sizes claim more than the file holds, or a member that inflates past its recorded size, now stops with exit 2 before memory or disk fills up.
  - `setup.sh --strchive-data` builds `og` before it removes an outdated catalog, so a failed build keeps the catalog that was there.
- Step 26b (fine-grained ancestry) now runs in the Rust `og` binary: `og ancestry-fine panel-map`, `check-map`, `order`, `sample-bed`, `chroms` and `report` replace the commands of `bin/ancestry_fine_report.py`, in the step script, the Nextflow module and `setup.sh --ancestry-fine-panel`. The module now keeps only the group names, colours and minimum that the report and the docs demo read. The outputs are the same, byte for byte, except as listed below. No option, output file or format changes. Steps 26b and the panel install now need `og`, and `setup.sh` builds it when it is missing.
  - A failed write no longer leaves a partial table. `sample-bed` used to write each level's ADMIXTURE input as it went, so a `.P` file with the wrong number of rows left the earlier level's `.bed`, `.bim`, `.fam` and `.P.in` behind for the next command. Every input is now read and checked first, and every output is written under a temporary name and renamed into place. `run_admixture.sh` comes last.
  - A missing or malformed input (a `.Q` or `.P` file that is not there, a position that is not a whole number, an RFMix file without its codes line) is now an `ERROR:` line and exit 1, not a Python traceback.
  - The genotypes VCF is read as a stream: only one byte per reference SNV is kept, whatever the VCF's size. On a synthetic panel of 500,000 SNVs, `sample-bed` takes 0.5 s and 67 MB, where the Python took 1.5 s and 370 MB.
  - The painting PNG has the same pixels. Its compressed bytes differ, because another deflate writes them. The comment at the top of `run_admixture.sh` names `og ancestry-fine sample-bed`.
- Step 27 (CPIC lookup) reads PharmCAT's report with `og pgx cpic-report`, in the Rust `og` binary, instead of `bin/pgx_parse.py`, which is gone. No output file, column or option changes.

- Four VCF filters of steps 04, 05 and 07 now run in the Rust `og` binary: `og sv inv-filter` (step 04), `og sv svlen-fix` (step 05), `og pgx refblock-fill` and `og pgx mito-merge` (step 07). They replace `bin/manta_inv_filter.py`, `bin/sv_svlen_fix.py`, `bin/pgx_refblock_fill.py` and `bin/pgx_mito_merge.py`, which are gone. Their output is the same, byte for byte, except for these fixes. Steps 04, 05 and 07 now need `og`: `scripts/setup.sh <genome_dir>` builds it, and `scripts/setup.sh --og` builds only it.
  - Step 05: an SV record whose INFO held `SVLEN` or `END` twice kept the old last value beside the new one. The rewrite now replaces the item it read.
  - Step 07: where the gVCF had a record at a multi-base PharmCAT position that was not a reference block, the input got that record and a 0/0 record at the same position. - Run logs in the Rust `og` binary. `og run state`, `og run eta`, `og run headroom` and `og run delta` read Nextflow traces, weblog messages, run-all.sh status and the per-box step history the way `bin/run_state.py`, `bin/run_eta.py`, `bin/run_headroom.py` and `bin/run_delta.py` do, and write the same files byte for byte; a parity test runs both on the same inputs. `og run tasks` gives the step of each trace row, and the Nextflow CI check of ClinVar reruns now reads the traces with it. Two fixes: a PRS percentile of 0 in the delta report now reads 0, not "none", in og and in `run_delta.py`; and `generate-report.sh` now compares a run with the newest `history/` folder that holds a summary.json, as the delta tool itself does: a newer folder without one, left by a copy that stopped half way, no longer stops the report with "the delta against the previous run was not written". og reads a trace memory cell such as "1.2.3 GB" as no value; the Python modules of the live alerts still stop on it.
- Rust building blocks for the ports that look things up by position. `og-io` reads the lines of a region from a bgzipped file through its `.tbi` or `.csi` index, as `tabix` prints them, reading only the blocks the index points at. `og-intervals` reads bases from an uncompressed FASTA through its `.fai`, as `samtools faidx` prints them, and refuses a compressed FASTA or a `.fai` that does not match the file. It also adds sorted interval sets (union, intersection, lookups by binary search, BED files such as the PAR regions) and reciprocal overlap. Nothing calls them yet, so no pipeline output, option or file changes.
- `og` runs natively on a Mac that hosts the live site, so the genome map works there too. `scripts/setup.sh --og` and each release now also make `og-darwin-arm64` and `og-darwin-x86_64`, and `bin/og` runs them on macOS. They are built without the new cargo feature `bam` (on by default, so the Linux builds are unchanged): the BAM tools say so and exit 2 there. `rust/og.sh check` refuses a stale macOS binary, and a release's `SHA256SUMS` lists all four.
